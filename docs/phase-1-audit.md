## 3. Backend contract (source of truth)

- Base URL: `{host}/api/v1`. Auth: `Authorization: Bearer <Sanctum token>`.
- Tenant headers: `X-Business-Id` (required for tenant routes; inferred when the
  user has exactly one active membership) and optional `X-Outlet-Id`.
- Envelope: `{ success, message, data, meta }`; errors
  `{ success:false, message, errors, code, request_id }`.
- Money: decimal strings with 4 dp. Timestamps ISO 8601 UTC. Pagination:
  Laravel `data/current_page/last_page/total/per_page`.
- Auth flow: `POST /auth/login` and `/auth/register` return
  `{ user, token }`; then `GET /me` returns memberships, roles/permissions,
  outlets and the active business's subscription summary. `POST /auth/logout`
  revokes the token.
- Multi-tenancy: `/me` + `/businesses` list memberships; switching business
  means changing `X-Business-Id` and re-reading `/me` (subscription is per
  active business). Outlet switching uses `GET /outlets`; non-owner/admin
  users are restricted to their `outlet_memberships`.
- Permissions: from the active membership role (owner gets everything);
  `platform.admin` / `is_platform_admin` only for the admin surfaces. The API
  enforces every permission, so mobile gating is UX only.
- Subscription: `EnsureSubscriptionActive` gates tenant routes; `/me` carries
  `status`, trial days, features, limits. Mobile shows status/trial and lets
  the web app handle billing checkout.
- Offline: `GET /sync/bootstrap` (needs `sales.create`) returns business,
  outlet(s), resolved menu (modifiers/availability), active payment methods,
  tax rates and recent customers. Queued direct sales replay through
  `POST /sales` with an `idempotency_key`; there is no separate replay endpoint.
- No web sockets. Orders/kitchen need polling (TanStack `refetchInterval`,
  paused in background).

## 5. Known gaps and constraints

1. **Barcode lookup** — no barcode route exists. Product list responses omit
   barcodes; only `GET /products/{id}` loads them. Phase 3 will support camera
   scan → SKU/name search, and flag a possible `GET /products/barcode/{code}`
   backend addition if true scan-to-cart is required (needs approval; no
   backend change in this project unless agreed).
2. **Google sign-in** — backend callback hands off to the web frontend; no
   mobile redirect/deep-link is registered. Deferred until credentials + URI
   exist.
3. **Variants** — variant selection is possible on sales lines; list-level
   inventory is product-level, and stocktakes count product-level only.
4. **Offline scope** — only direct `POST /sales` is safe to queue (idempotency
   key). Open-tab checkout, order edits, transfers and counts stay online-only.
5. **Local API from Android** — emulator reaches host via `10.0.2.2`; a
   physical device needs the LAN IP. Plain HTTP needs a debug cleartext config;
   production must be HTTPS.
6. **Runtime verification** — no emulator currently attached. Build/runtime
   checks need one (or a device) plus `JAVA_HOME` pointing at Android Studio's
   JBR.
7. **Tests** — none configured; Phase 8 adds focused unit tests (money formatting,
   idempotency-key generation, offline queue replay/dedupe) via jest-expo.
8. **Template debt** — demo screens/components (`explore`, animated icon, web
   badges) will be replaced, not extended. The pre-existing 3 typecheck errors
   must be cleared before feature work.

## 8. Phased plan

### Phase 2 — Foundation
- Env config (`EXPO_PUBLIC_API_BASE_URL`, example file), axios client with
  envelope/error/401 handling, secure token store, session restoration,
  QueryProvider, AuthProvider, TenantProvider (business/outlet switching +
  permissions), theme provider with light/dark tokens, Plus Jakarta Sans,
  copied brand assets, app name/scheme/icon updates.
- Fix the 3 template typecheck errors, add ESLint config.
- Acceptance: `npx tsc --noEmit`, `npx expo lint` clean; login → `/me` →
  business/outlet selection works against the local API; token survives reload.

### Phase 3 — Core UI
- Shared UI kit, app header, custom bottom tabs, More (permission-filtered),
  business/outlet switcher, dashboard, product catalogue + detail/search,
  loading/empty/error states, pull-to-refresh.
- Acceptance: dashboard and catalogue render real API data; no dead buttons;
  permission-filtered navigation.

### Phase 4 — POS
- Product/category browsing, search, cart (persisted), quantity/discount,
  server-priced preview (`/promotions/preview`), tax/payment methods, checkout
  with idempotency key, receipt with change, void where permitted.
- Acceptance: a real checkout against the API succeeds; duplicate tap with the
  same key returns the same sale; totals come from the server.

### Phase 5 — Operations
- Orders (list/detail/create/status/cancel), kitchen board (polling),
  inventory (balances, movements, adjust, low stock, transfers, stocktakes),
  customers (CRUD/profile), purchasing (suppliers, POs, approve, receive),
  shifts (registers, open/close, cash movements, history).
- Acceptance: each mutation hits a real endpoint and invalidates its queries;
  permission-denied paths handled.

### Phase 6 — Reports and settings
- Sales summary, sales by product, inventory/low-stock reports, optional
  plan-gated advanced cards; account, business/outlet info, change password,
  theme, logout; subscription status/trial banner.
- Acceptance: report ranges/outlet scoping correct; settings writes persist.

### Phase 7 — Offline
- `sync/bootstrap` snapshot cache keyed by business+outlet, cached dashboard,
  persisted cart, durable direct-sale queue with idempotency keys, connectivity
  banner + sync status, retry on reconnect, duplicate prevention.
- Acceptance: browse catalogue and build a cart offline; reconnect replays once;
  server refusal surfaces (not swallowed); unsupported operations clearly
  blocked.

### Phase 8 — Verification
- Unit tests (money, idempotency, queue), TypeScript, ESLint, `expo-doctor`,
  Android build (`npx expo run:android` with `JAVA_HOME` = Studio JBR),
  emulator runtime smoke, API integration checks (login, tenant switch, sale,
  order, inventory read).
- Acceptance: all checks pass or failures are reported with causes; no feature
  claimed without exercising it.
